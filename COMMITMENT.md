## 8. Gates, outcomes and runs not completed

- A pass is graded by the gates of the frozen rubric, in this order; the first that fires decides:
  1. a gold hit row answered clear: `failed`, gate `missed-sanction`;
  2. hold on every row: `failed`, gate `all-hold`;
  3. more hold answers than `rubric.holdMax`: `failed`, gate `hold-max`;
  4. hit precision (correct hits over hit answers) below `rubric.hitPrecisionMin`, not applied without a hit answer: `failed`, gate `hit-precision`;
  5. hold answers at most `rubric.worksHoldMax`: `works`, gate `hold-works`;
  6. otherwise: `works-with-controls`, gate `hold-controls`.
- A hit is credited by the answer. Beside it, without a gate, every completed pass shows `hitEntityMatch` and `hitNoListCall`. An invalid row within the tolerance (`rubric.invalid.maxRows`) counts as a hold answer, except a row lost to the connection with the model provider.
- Outcomes: `failed`, `works`, `works-with-controls`. There is no readiness label.
- A missed sanction (a gold hit answered clear) fails the run, and nothing compensates for it.
- The passes combine by `repeats.aggregation`: the run is graded by its worst pass. A missed sanction in any pass fails it. The bound is `intervals.method` at `intervals.level` for `intervals.metrics`, over the gold hit rows of one pass; passes go over the same rows and are not pooled. The bound describes this SAMPLE book, not the task class (`intervals.scope` in every receipt).
- "Not completed" is a status of the run, not an outcome. A run is not completed when, and only when:
  - a list request failed after retries, in the probe or in any row, in the baseline or in the model's tool;
  - a response of the list was not JSON or had no results for a query;
  - a response of the list carried a version different from the list version; with `versionCheck` `"response"`, also a response that carried none. With `"description"`, a response without a version does not stop the run;
  - a row did not assemble from the export;
  - a pass had more invalid rows than `rubric.invalid.maxRows`, an invalid row on a gold hit row, invalid rows only, or any invalid row lost to the connection with the model provider: a network error, a timeout, HTTP 429 or 5xx after retries;
  - a pass was not completed, or the run made fewer passes than `repeats.n`;
  - the run ended without a receipt: stopped by a signal, failed with exit code 1, or cut off by a machine failure.

  Refusals before any network call (by digests, configuration or empty files) are not runs and write nothing.
- A run not completed has one possible verdict, `failed`: for a missed sanction in an answered row of any pass; for a completed pass of the same run that failed; or for a failure of the stopped pass that its answered rows already make certain: more hold answers than `rubric.holdMax`, or a best reachable hit precision below `rubric.hitPrecisionMin`. Gate and pass are those of the first pass that failed, as for a completed run.
- Publication. A run that fails is published under the same rules as one that passes. A run not completed is published with its status and its reason; it has a verdict only under the conditions above. The baseline goes first. The model runs only after an attempt of the baseline that completed and passed the comparison of section 9; if the attempts of the baseline end without such an attempt, there is no model run under this commitment. The receipt of every attempt is published at any outcome.
- Reruns.
  - A rerun is allowed only after an attempt not completed whose receipt says `rerun: "eligible"`: for the model only when that attempt has no verdict, and with a verdict the kit sets `"not-eligible"`; for the baseline also when it has the verdict `failed`, because the baseline is deterministic and its expected result is declared before the run. ## 13. Limits of this commitment

- The digests fix the bytes. They say nothing about when those bytes came into existence.
- The transparency log entry and the timestamp token show that this file existed no later than their time. They do not show that the runs came after it: no value that becomes known only after signing enters the runs, so there is no lower bound on the time of a run.
- Pre-registration shows that the expected figures were not edited after the result. It does not show that nobody knew them: the figures of the baseline come from the closed rehearsals (section 10). The model has no expected figures.
- Numbering makes selective publication detectable; it does not prevent it.
- Freezing a file does not make it correct. It makes it identifiable.
- The bound describes this SAMPLE book, not the task class.
- Nothing here supports a conclusion about another list, export, book, model or setting, or about the screening of any institution. This is not an audit.
- Re-scoring shows that the published figures follow from the published decisions under the frozen rubric. It does not show that the model gave those decisions: only an own run checks that, and only by outcome, not byte for byte.
- The kit fixes the export and the software, version and parameters of the matching server, not its search index. Two builds of the index can differ in their statistics (BM25 term statistics, deleted documents, shards), and so in the candidates the server takes from the index and in the order of candidates with equal scores; equal scores themselves are not the cause. Among candidates with an equal highest score the baseline takes the one with the smallest id, so the order alone does not change a decision row. This holds only as long as the server returns every candidate with the highest score: where it returned exactly its limit and all of them had the same highest score, it may have left out an equal one (section 9). The byte-for-byte agreement of the baseline rows was measured on three builds of the index on the same machine, counting the first attempt of the rehearsals (sections 9 and 10), not on any machine, not on the build planned for the public runs, made after the rehearsals, and not on any later build: the public baseline run is the first measurement on the build it runs on. Any divergence is a finding of the calibration (section 15), not an allowed deviation.
- With `versionCheck` `"description"` the list version comes from `snapshot.json`, not from the server. The kit does not see from which export the index of the server was built; that rests on the build of the index by the party that executes the runs and its check of `/catalog` (section 5).
- The model is a service of its provider and is not deterministic. This commitment fixes the model id requested and records the id returned; the agreement of the three passes (`agreement` in the receipt) shows the spread of its answers.
- The leak check (section 8) runs over the run logs, which are not published; a reader cannot repeat it.
- An own run needs a copy of the same export, byte for byte, and the export is not published by us (section 5); this commitment does not promise how a reviewer would obtain it.
- The run on the local stub checked the mechanics of the runner on the answers of the stub, invented text and a tool call that repeats the row it received (section 10); it says nothing about the behaviour of the model.
- The digest check at start is part of the runner itself: a changed `run.mjs` may not call it, and then its silence proves nothing. The bytes of the kit are checked by outside means (`sha256sum -c SHA256SUMS` and the comparison of `SHA256SUMS` with the signed `kit.files`, section 14), not by the kit.
- The kit does not link or count attempts; that every attempt is published rests on this commitment and the signed result manifest, not on the kit.
- The party that executes the runs can itself cause a failure of the list or of the connection: the matching server is local, the network is in its hands, and the answers of the model are visible to it in the log while the run goes on. The rule keeps a cut-off pass from escaping a failure that its answered rows already make certain, and limits cut-offs to two reruns per mode, but it does not tell a real failure from a caused one. A cut-off can still take a pass away from a failure that is not yet certain, and away from `works-with-controls`; the hold count of that rule counts only hold answers, not invalid rows.
- The order of the attempts rests on the clock of the party that executes the runs: the time in `runId` and in the receipt is written by its machine.
- The signatures show the same email address, confirmed by a sign-in to GitHub through Sigstore at each signing time. They do not show one person, and `cosign` does not check that the GitHub account was the same.
- Neither this commitment nor any receipt names the address of the model provider: an intermediary on the way to the provider could turn an answer of the model into HTTP 5xx, and the retry of the request would ask the model again about the same row. The proxy of section 6 is such an intermediary: it can cut a connection, and the cut request is retried.
- Receipts do not cover a run stopped by a signal, a run that failed with exit code 1, or a run cut off by a machine failure. Such a run is disclosed by a record with its `runId` and the SHA-256 of its log as left on disk, or the statement that no log was left (section 8); its rows are not published, its result is not completed, and no rerun follows it. A missed sanction in such a run is not visible.

## 15. External check after publication

These rules hold for any external check. This commitment does not say that one will take place or who would make it.

- Re-scoring. From the published kit, a published receipt and the result manifest, without network, keys or export: `node run.mjs --rescore <receipt> --manifest <result manifest>`.
  - Before re-scoring, the mode compares the SHA-256 of the receipt with the list of the manifest. A receipt not in the list gives `RESCORE mismatch class=binding key=manifest`, exit code 6, and no re-scoring.
  - The signature of the manifest is checked by `cosign`, not by the kit.
  - A match is the last line `RESCORE match` and exit code 0; a divergence is `RESCORE mismatch` and exit code 6.
  - The `UNVERIFIED` lines name what re-scoring cannot check: the assembly of the rows derived from entities without the export, and the stops of the runner. Without `--manifest`, they add that the receipt is the published one: a match then shows only that the figures of the file follow from its own rows.
- An own run follows the steps of the section "Re-executing a run" of the README of the kit; the README is a file of the kit, with its digest in section 4.
  - Conditions: the same frozen kit; the same export, byte for byte (`exportSha256`, section 5); the same matching server (software, version and parameters from `snapshot.json`, with an index the reviewer builds on this export); the same configuration of the candidate and of the run (sections 6 and 7); Node.js of the same major version as `runtime.node` of the published receipt.
  - The kit checks the digest of the export itself; it does not see the software and version of the server, which the reviewer names; it checks the list version as section 5 says. With `versionCheck` `"description"` it does not see from which export the index was built: the reviewer checks `/catalog` of its own server, as the party that executes the runs did (section 5).
- Calibration, the first two steps of the README:
  - `sha256=` in the line `ASSEMBLY` equals `input.assemblySha256` of the published receipt;
  - `--baseline` reproduces the decision rows of the published baseline byte for byte, every row without exception: the line `DECISIONS pass-1` equals `passes[0].decisionsSha256` of the published receipt and the expected value of section 9. The same outcome with another digest means the calibration failed.

  If the calibration fails, the own `--model` is not compared with the published one, and the divergence of the calibration is a finding; the reviewer names the rows where it occurs by `id` and key path.
- Comparison. The result over the attempts, by the rerun rule of section 8, under the same thresholds, equals the published one. Beside the result, for both runs, are given the missed sanctions (k of n) per pass, the hold answers per pass and the hit precision per pass. No byte-for-byte agreement is required. Another result is a divergence. The same result under another gate is a finding. Both are published, and the divergence is stated before any explanation (the formula of section 9).
- A run on another export is a separate result, not a re-execution (section 12).
